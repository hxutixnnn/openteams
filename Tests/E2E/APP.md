# Native app E2E: performance regression journeys

These scenarios run the OpenTeams app and its production conversation views and rich editor. The standalone Swift programs beside this document are supplemental core workflows and benchmarks, not app-level E2E tests.

## Prepare and launch

Run `python3 script/prepare_app_e2e.py`. It builds the debug product directly, copies it into a new temporary bundle with a unique identifier, ad-hoc signs that copy and prints its absolute path and storage root. It does not launch, install, stop or replace any app, use the normal signing identity or package a credential helper. Keep the printed root for restart checks; running preparation again creates a different fixture.

Launch that exact bundle through the mounted native computer tools with background delivery. Name/bundle-ID lookup failed for temporary fixtures in QA. The mounted Finder exact-bundle-URL route unexpectedly brought the fixture forward despite background delivery and is unusable for background acceptance. Do not repeat it. QA also tried the direct exact-bundle path through the mounted background launcher and received `APP_NOT_INSTALLED` despite a valid signed bundle. That route is stopped too; do not retry it unchanged. If no permitted route opens or reopens this bundle, record that step as blocked. Do not use shell UI, installation or registration workarounds. Inspect its window before interacting. The fixture skips explicit startup activation and notification registration, uses an accessory app policy and disables account settings. Initial app objects use no demo-drafts file or normal read-cache path. The displayed fixture uses only intercepted fictional HTTP and disables media clients. Its two conversations share the same IDs across fictional accounts to expose account-isolation failures. Its stored drafts and read cache live below the printed temporary root. Missing or invalid fixture metadata displays an error instead of the normal app.

Use the mounted native tools for every UI interaction, with current window/element handles and background delivery. A refused background operation is a verification gap; do not substitute shell-driven UI automation or foreground input. Foreground handling on the host requires the person's explicit agreement; native sheets, menus and confirmations can change focus. Do not repeat the previously focus-changing Delete route without that agreement, or operate on an earlier fixture left open at confirmation. Preserve snapshots and exact step outcomes outside the repository. Do not infer FPS or input latency from successful interactions.

1. Confirm the fixture header shows `fixture-a` and `Ready`, and `Fictional project` is selected.
2. In `Message composer`, enter `Fictional recovery Xin chào 👋`. Reveal formatting, toggle Bold, and append ` Bold tail`. Insert two new paragraphs containing `First item` and `Second item`, apply Bulleted list to the final paragraph, then insert Ada Example through the Mention menu. Record the rendered editor and exact text. The saved document must contain plain and bold runs, a paragraph, a bullet-list item and the mention identity.
3. Select `Fictional planning`. Its composer must be empty. Enter `Planning draft`. Return to `Fictional project`; verify the original rich text, formatting and mention. Read the JSON below `ReadCache/Compose` to confirm matching persisted blocks/runs/mention identity and mode 0600. No fixture control may set these drafts directly.
4. Click `Quit Fixture`. Verify this fixture process/window closed. Relaunch the same bundle, select `Fictional project`, and verify the native editor restores identical text, bold/list formatting and mention. Verify the planning draft also restores. Compare saved rich JSON before and after restart.
5. Click `Account B`; the same conversation IDs must have empty drafts. Type `Account B only` in its actual editor. Click `Account A`; the original A rich draft must return. Switch B/A again and verify separation, including after another fixture restart.

## E2E-2: row actions after refresh and paging

1. In Account A / Fictional project, confirm message 100 is visible. Use its production context menu: Reply must populate a reply preview; Cancel reply must remove it. Edit Message must open the production editor with that message; cancel without saving. Delete Message must be enabled for this own message.
2. Click `Append and refresh`. Message 101 must appear through the normal reader refresh path. Repeat Reply and open/cancel Edit Message on message 101. Confirm the composer draft survives the refresh and edit cancellation.
3. Scroll to `Load Older Messages` and press it. Messages 61–80 must prepend in order. Verify message 80 can Reply and open/cancel Edit Message. Record the visible anchor before/after paging; verify it is retained. Return to the bottom and verify actions on message 101 still target 101.
4. Delete message 101 using the production confirmation only when the screen route allows foreground modal behavior. Native confirmation can activate the fixture even when invoked through background accessibility actions; this was observed in the implementation owner's run. If activation occurs unexpectedly, stop the screen route immediately and record this step as blocked. When permitted, the fictional transport accepts the request and returns a strictly newer deleted version scoped to the current account, conversation and message. Verify the row becomes `Message deleted`, the pending deletion and Check status control clear, and Reply/Edit/Delete are unavailable. Also edit a different own row through production Save before deleting it; its deleted version must be newer than the edited version and must reach the same tombstone. Compare the other account/conversation and neighboring rows, which must remain unchanged. Confirm neighboring message 100 still has its own correct actions and the draft is retained.

## E2E-3: react to an original absent from loaded history

1. Use a freshly prepared bundle and temporary root. Confirm `fixture-a`, `Ready` and `Fictional project`. Enter `Reaction journey draft A` in the actual `Message composer`. Record the native conversation and its saved history below `ReadCache`: recent messages are 81–100, or 61–100 after one older page. Message `1800000000050` must be absent from loaded/saved history throughout this journey. The transport never includes it in either history page.
2. Find `Fictional message 99`. Its quote shows Ada Example and `Context-only message 50`. Click that quote's production `Show original message` button. Do not use a fixture control or directly call a store method. The production `Message context` sheet must show `Original message`, Ada Example and `Context-only message 50 · fixture-a`. It contains only message `1800000000050`; message 99 stays in the conversation behind the sheet.
3. Open the context row's production `React` menu and choose `👍 Like`. The fictional endpoint accepts only Like/Remove Like on message `1800000000050` in `fixture-one`, using the current fictional account's token. Wait for the production targeted refresh: the original's reaction chip must show Like with count 1, and accessibility must say `includes you; remove reaction`. Reopening `React` must offer `Remove 👍 Like`. There must be no reaction error or unresolved `Check reaction` control. This verifies `canReact` falls back to context when its history index has no matching ID; a direct action on message 99 does not cover it.
4. Choose `Return to conversation`. Message 99 and neighboring message 100 must have no Like chip; the composer must still contain `Reaction journey draft A` in `Fictional project`. Reopen message 99's original and verify A's Like remains. Return again, click `Account B` and select `Fictional project`. Its composer must be empty; type `Reaction journey draft B` in the actual editor and reopen the same quote. The original must now say `Context-only message 50 · fixture-b` and have no Like chip; `React` must offer `👍 Like`.
5. Like the original as B through that same production menu, then verify count 1 and `includes you; remove reaction`. Return, switch to A, select `Fictional project` and reopen the original: A's count must still be 1. Choose `Remove 👍 Like` as A. After targeted refresh the chip must disappear and `React` must offer `👍 Like`. Return and reopen as B: B's Like must remain count 1. Remove it through B's production menu and verify its disappearance. Return as A and verify its original remains unreacted, neighboring rows remain unreacted and the original is still absent from saved history. Each return to A/B must restore that account's exact composer text without mixing the drafts.
6. Quit only this new fixture with `Quit Fixture` and verify that its window/process closed. Reaction state is intentionally in memory for this process; a restart resets both accounts' fictional server reactions. Do not count restart persistence of reactions as a postcondition.

Record the original ID, account-specific original text, chip/accessibility state before and after each action, selected account/conversation, saved-history absence, neighboring-row states and composer text. Retain snapshots of the actual production context sheet and menus. Only Like and Remove Like are supported by this fixture; other reactions and all send requests remain rejected. The transport has no network fallback, accepts only the fictional accounts, and returns reactions only for the original in `fixture-one`.

## Evidence and limits

Record the commit and source hashes, bundle binary hash, temporary root, process/window IDs, actual editor text and persisted rich JSON, and per-step passed/failed/blocked status. Restart means terminating and relaunching this same fixture process, not constructing another store in a test executable. The supplied fixture rejects unsupported requests, including sending and reactions other than the context-original Like scenario above. Existing intercepted core workflows separately cover send uncertainty and recovery.

Manual app E2E outcomes are distinct from performance benchmarks. Native FPS/hitch tracing, startup timings, rapid typing/IME, selection, accessibility and live-service behavior require their own evidence. If a step cannot be completed with the approved background route, report the exact step as blocked and withhold any claim that the full journey passed.
